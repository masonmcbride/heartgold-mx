# Playable integration: the execution path

Current viewer behavior is documented in [New Bark walking](player-movement.md): keyboard movement, native directional stepping presentation and smooth camera following are now connected. The subsequent [background interaction](field-interaction.md) adds original event selection and sign-bytecode dispatch with native dialogue presentation. The sections below retain the progression and distinguish original gameplay execution from native presentation.

The target is an original-game session with movement, interaction, transitions, battles and saves. A larger map gallery is useful supporting work, but map rendering counts do not measure progress toward that complete session.

## Original application orchestration now runs

The complete unchanged `src/overlay_manager.c` is compiled, linked and executed. All seven original functions are exercised: New, Delete, CreateAndGetData, GetData, FreeData, GetArgs and Run. The original state machine advances init, exec and exit across repeated calls, retains each phase's procedure state and resets that state on phase changes.

The Cocoa viewer now uses `HGFieldApp` instead of directly owning a scene. `HGFieldApp` gives original `OverlayManager_Run` native scene-init/exec/exit callbacks. A successful map change constructs a new application, exits the old one through the original manager and resets its camera. Failed initialization also exits through the original manager and frees its resources. A later [field-task integration](field-task-runtime.md) now runs original task/application dispatch on a native timer, with redraws independent of simulation. This remains a native scene application, not the original field/game loop. Original `FieldMap_Init/Main/Exit` are still unexecuted.

This is an application-lifecycle dependency used by field, menus and battles. It does not make their original overlay callbacks available automatically. Native callbacks are explicitly named `scene_init`, `scene_exec` and `scene_exit`; they must not be presented as original field/gameplay routines.

`hg_overlays` has a scoped compatibility interface. `FSOverlayID` is signed 32-bit identity; original manager structures use native pointers, not the serialized DS ABI. `HandleLoadOverlay` and `UnloadOverlayByID` implement explicitly admitted static module residency. Unknown/unregistered, duplicate or invalid residency requests abort with a named diagnostic. Only the asynchronous load request used by the original manager is supported; the native operation is immediate. No DS binary overlay loading, relocation or SDK execution is claimed. The actual scene application uses `FS_OVERLAY_ID_NONE` because its callbacks are already linked.

Tests run yielding init/exec/exit callbacks, assert phase-state resets, exercise all original data/argument APIs, validate residency before/during/after completion, and reload the same manager template. They also repeatedly render and close New Bark and the corrected player house through the real scene application, including recovery from invalid initialization. Synthetic callbacks establish manager behavior, not original gameplay.

## Why these changes precede more rendering features

The earlier 186-map “geometry failure” bucket contradicted the existing corpus test: all 676 land scenes already decoded successfully without a rendering callback. The rejection was in the viewer's assumption that every surface had a texture. Connecting its existing untextured raster path, while initializing opacity for those materials, unlocked many maps without new decoding instructions.

Visual inspection then exposed another category error: area type 0 requires indoor prop models and indoor shape metadata. The native boundary had been reusing outdoor resources. Correcting both together follows original area-loader relationships, produces an actual player-house interior and rejects unsupported indoor models honestly. Current raster completion is 453/540 entries; it is not a port-completion percentage.

The application manager is the next shared dependency because the original game organizes major behaviors as applications with explicit lifetimes. Bringing that manager into the running app gives future integrations a real orchestration path instead of adding independent demos for each system.

## Remaining critical path

1. **Original field execution ownership.** Bind persistent resources, original object/avatar state, input and task progression under a continuous field update. Original field-task/application dispatch is now connected in the native scene app. Existing system-task queues and the static Thumb height solver are separately tested; scoped avatar/object collision and original normal-walk command updates now execute, while the complete field loop remains unconnected. Compile/link coverage alone cannot satisfy this gate.
2. **One original movement and interaction cycle.** Test input -> original avatar/object update -> terrain/occupancy decision -> resulting position, followed by an event interaction. Do not substitute a native camera marker or a terrain-only walkability guess.
3. **Original transition and script ownership.** Exercise a map-header crossing and an interior transition with original event/object reconciliation. Decode event/script resources from original manifests; execute original routines where available.
4. **Persistent game state.** Establish original save structures/checksums and a host filesystem boundary, then verify save/reload round trips before exposing persistence in the app.
5. **Battle and remaining platform services.** Original battle/application dispatch, audio, animation, missing graphics semantics and ARM-only routines must be admitted with explicit executable boundaries. The current Thumb engine covers only the tested terrain subset.

A complete native build is not achieved by adding declarations until the compiler accepts every file: original code directly accesses DS hardware, many APIs require implementation, and native pointers do not preserve the 32-bit DS ABI. The whole-source audit remains compile-only and does not execute output. Its baseline compatibility pass emits 32 of 415 surveyed C objects; scoped targets such as the new overlay manager are separately compiled/executed with their dedicated boundary. The audit's ARM64 attempts reject the original ARM/Thumb assembly, while the separate terrain path assembles Thumb and interprets its enabled instructions. These are different execution routes and must not be combined into a misleading coverage percentage.

Whole-game hardware emulation is a separate route to full play-through. This native port does not yet implement that complete hardware environment or provide a compiled playable game. No reliable completion date follows from current map coverage. The engineering priority is the smallest verified original gameplay cycle, then broadening that connected cycle rather than accumulating isolated features.

## Original motion execution boundary

`hg_motion` compiles the complete unchanged `map_object.c` and `player_avatar.c` with a scoped native compatibility header. `original_motion_state` links and executes original avatar creation around an active original object, save-state initialization, facing and coordinate access. The native owner is not the serialized DS `FieldSystem` ABI. Unused functions are discarded by the Apple linker; their dependencies have declarations, not success stubs. Full-source compilation therefore does not establish full avatar/controller functionality. In particular, unused upstream paths retain pointer-width assumptions and invalid-parameter missing-return warnings.

`prepare_field_guest.py` assembles seven complete original movement/field assembly units and three original data-table units into a build-local, relocated Thumb image. Its provenance records source hashes and the image hash. The current image is 27,660 bytes with 377 named unresolved imports. Only explicitly admitted native providers can satisfy an executed import. An unprovided service fails execution. These counts measure assembled coverage, not executed gameplay.

`motion_guest.c` executes original directional-input resolution (`sub_0205DDD4`) and original grid-step bookkeeping (`sub_02060F24`, including original direction-delta helpers). Guest opaque handles resolve to original native C getters/setters; native pointers never enter guest registers. Execution has bounded RAM and an instruction budget. A failed grid-step restores the original object. The API deliberately performs no collision admission: callers must not expose it as walking through the map. Tests cover all cardinal directions, idle input, previous/current coordinate consistency, a closed round trip, and invalid direction rejection. Original `PlayerAvatar_MoveControl` remains unconnected. The integrations below connect scoped player collision, movement commands and native actor rendering.

The Thumb interpreter now admits the additional bitwise, register rotate, signed-load and Thumb register-branch forms needed for this assembly integration. This remains a bounded source-execution boundary, not DS hardware emulation or a complete ARM CPU.


### Original field attributes and occupancy now execute

`hg_motion_tile` marshals the normal-field dispatch pointer and map-loader handle into guest RAM. Original `sub_020548C0` and `GetMetatileBehavior` call original `sub_020547D8`, which selects the land attribute array and computes the tile offset. The two native map-loader providers resolve validated resources and copy the original 2,048-byte attribute array. The original assembly extracts the wall bit and behavior. No native `FieldSystem` is reinterpreted as a DS structure. Missing resources fail the public query and preserve its output.

`hg_motion_terrain_barrier` evaluates original `sub_02060DEC` using the original native metatile predicates selected by its original function-pointer tables. A private object copy receives the current tile's cached behavior through its original setter; the live object is unchanged. Target coordinates come from the original grid-step routine. This query combines wall and directional barriers only: it does not authorize movement without height, occupancy and player-mode checks.

`hg_motion_occupied` executes original `sub_02060BFC` against a bounded array of native original objects. Explicit guest handles represent the manager and each object; iteration calls the original native `MapObjectArray_NextObject`. Original code skips the querying object, inactive objects and flag-18 objects, checks both current and previous tiles, and requires vertical separation below two object-coordinate units. Empty/oversized managers and objects outside the supplied manager fail. This is one original occupancy routine, not the full offline/follower-aware player collision controller.

The motion test checks all 1,024 New Bark tiles (609 walls, 415 non-wall tiles), all 3,968 in-chunk directed neighbor edges (2,320 rejected by wall/directional rules), and verifies that barrier queries do not mutate the live object. The test oracle reads decoded attribute bits and independently selects the appropriate original metatile predicates. Synthetic three-object tests cover each querying-object position in the array, previous/current occupancy, vertical separation, inactivity, flag 18 and invalid manager rejection. Resource-backed field checks and synthetic occupancy checks remain distinct evidence; original map-event NPC population is not yet integrated.


### Static New Bark player collision and discrete walking

`hg_motion_player_collision` now executes original `sub_0205DA34` and its reachable helpers, including range checks, `sub_020549F4`/`sub_02054954` height admission, object occupancy, directional barriers, ledges/doors, water requirements and cycling restrictions. Native original avatar getters provide the player state; original metatile predicates execute the original rules. The query refreshes the object's behavior cache temporarily and restores the entire object before returning, including on guest failure. Unknown providers report a named execution failure. Unsupported environments preserve the caller's output.

The admitted environment is now New Bark and its seven tested interiors (current and target must share an admitted header), normal static terrain, no active gym gimmick and no dynamic platforms. The guest dispatch table uses a native static-height provider in place of original `sub_02054654`'s dynamic terrain/chunk-cache selection. The provider accepts nonnegative matrix-global Q12 coordinates and calls the existing original Thumb BDHC solver with nearest-reference selection, including intermediate walking positions. Original `sub_02054954` still makes the height-threshold decision. A missing height fails execution instead of being silently treated as flat ground. `Gymmick_CheckCollision` is an explicit no-active-gimmick environment boundary here; its original C dispatcher is not executed. These boundaries must be replaced or extended before admitting gym/dynamic-platform environments. This is not full field-controller execution.

`hg_motion_walk_step` connects original direction resolution, the full admitted collision mask, original grid stepping and original Q12 tile-center conversion (`sub_020611C8`). State 0 walking commits a private object candidate only if the original mask is zero and target height resolves successfully. Previous/current grid coordinates, vector height and facing are updated through original native setters. Nonzero masks preserve object state, including special movement requirements: jumps, surf actions, doors/warps and scripts are not replaced with ordinary walking. Cycling and surfing are queryable collision states but are not admitted by this discrete walking API. This discrete API remains a test/integration utility. The viewer now uses the [original walking command dispatcher](original-walking.md) for incremental object movement; full input-controller and sprite-animation execution remain pending.

Tests exercise all 3,968 New Bark in-chunk neighbor edges through both the original player collision query and discrete walking integration: 1,590 commit and 2,378 are denied. Each committed move verifies original previous coordinates and exact vector/grid/height consistency; each denied move verifies unchanged object state. The height gate is checked immediately below and at the original 20-unit threshold in both directions. All 55 water-target edges additionally check original cycling rejection. Idle input, non-walking API rejection and unsupported coordinates preserve state/output. A synthetic second actor placed on a verified open New Bark edge also reaches the full original player occupancy mask and prevents the connected step. These are resource-backed execution tests with synthetic actor state. Native viewer controls now use the same collision admission followed by original movement commands; original NPC population is still absent.

The [original locomotion integration](original-locomotion.md) now executes the zero-collision walk/run branch of `sub_0205D4B4`, original input-axis history updates, step statistics and a follower notification mirror. The complete unchanged original statistics and math C units compile, and the specific statistics/encryption/RNG functions documented there execute and pass behavioral tests. General save loading and full field-controller execution remain pending.

The [original transition integration](original-transitions.md) now executes seven unchanged C function slices for warp selection and destination-anchor initialization, along with original event parsing and local-field records. This connects all 14 portals across New Bark’s eight-map network to native scene replacement. Full transition tasks, map-init scripts, NPC reconciliation and outdoor map-header crossing remain unexecuted; the complete field-control and warp-task C units are not claimed as compiled.
