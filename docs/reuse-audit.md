# Reuse decisions for continuous gameplay

Audit date: 2026-10-17. The objective is the least new code needed for correct continuous gameplay. A smaller implementation is useful only when it preserves the original behavior and makes the connected game session easier to finish. The proposed 60–80% reduction and 9k–25k LOC range are hypotheses; this repository does not yet have evidence supporting either estimate.

## Measured scope

Run the read-only inventory after a normal configure:

```sh
cmake -S . -B build
cmake --build build --target reuse_audit -j 6
ctest --test-dir build --output-on-failure
```

The target builds current executables and emits ignored `build/reuse-audit/functions.csv`, `inventory.json` and `REPORT.md`. The CSV inventories each emitted C/Objective-C text symbol, its translation unit, binding, proposed reuse decision and global-symbol presence in current applications/tests. JSON adds source/object/product hashes, the complete guest import list and lexical direct-call/provider hints for original startup/field entry points. Static function names are not attributed to final binaries by name because multiple source units use names such as `run` and `boundary`. Source provider hints cover the selected game manifests, not SDK subprojects. Calls through callbacks/tables and preprocessor semantics require further inspection.

The first snapshot before adding the audit tool has 66 compiled translation units, 17 unchanged game C units and 1,307 emitted text symbols, including test/static/header-generated functions. Of these, 723 symbols occur in original-game translation units; 112 original-game global text symbols are present in the field viewer. Neither number measures functions executed. There are 2,932 physical lines of compiled project C/Objective-C, excluding original source, tests, headers, Python and generated files. Dense source formatting means line counts are especially unsuitable as effort estimates.

The first audited field guest image had 213 external imports. Source inspection finds named conditional provider branches for 53 and no provider branch for 160. This is whole-assembled-unit coverage, not the imports reached by ordinary walking. Most unsupported imports have original game implementation candidates in the manifests. Three lack function-provider hints (`_020FD198`, `_s32_div_f`, `gMovementCmdTable`); this is not proof they lack data/library implementations. The audit parser indexes function declarations, not arbitrary assembly data labels or SDK libraries. A provider branch can intentionally reject inputs or admit a narrow environment, so even 53 is not a supported-API count.

The existing behavioral tests and prop instrumentation remain execution evidence. This new audit reads build artifacts and sources; it does not instrument or execute game functions. It does not establish the minimum SDK set needed to boot the complete game. The older whole-source compiler survey is a different measurement with different compatibility headers; its object count must not be added to the current integration count.

Dynarmic is a CPU translator, not an SDK implementation or a complete privileged ARM9/ARM7 environment. MMIO, TCM/VRAM aliases, interrupts, IPC, cache effects and hardware-driven scheduling either need real support or an explicitly intercepted path. Apple JIT memory/signing behavior must be validated for the intended executable configuration. Do not copy an example's out-of-bounds zero-return behavior into our memory contract. Do not silently interpret fallback as success. Keep unsupported instructions/services visible.

## The ABI decision that determines cost

Current native objects contain 64-bit host pointers. Guest registers contain 32-bit addresses or opaque handles. A JIT cannot make original assembly dereference a native `LocalMapObject` or the scoped native `FieldSystem` safely. Native function pointers cannot simply be put in guest callback tables. Many original algorithms also access fixed structure offsets and embedded arrays without calling an accessor.

For every admitted subsystem, choose one authoritative state representation. Native-owned objects can remain native if all guest accesses pass through typed accessors/marshaling. A subsystem with pervasive direct offset access may be cheaper to keep together in serialized guest memory and expose coarse native calls. Avoid maintaining two independently mutable object graphs. Trace ownership and callback paths before choosing the boundary; promoting arbitrary pointers to guest addresses is not a shortcut.

Keep the current source tree until this choice is demonstrated. `ds_platform` already distinguishes shared byte/graphics support from HeartGold resources and policy. A future `nitro-mx` extraction should follow a second independently exercised game, not precede it as a directory-only milestone. No Bowser's Inside Story code/assets are present in this audit, so compatibility with it is not established.

## Smallest useful next sequence

1. **One backend comparison, not a second CPU project.** Pin and build a reviewed Dynarmic revision in ignored build inputs. Configure ARMv5TE explicitly. Run the same existing original height and movement corpus through callbacks, including opaque native handles, interworking, deliberate memory faults, service failures, instruction budgets and overlay/code invalidation. Compare outputs and modified state to current tests; measure steady-state execution and startup/memory cost. A passing README example is insufficient. Retain the interpreter until the replacement preserves the contract. Do not add a speculative common CPU framework first.
2. **One original continuous field owner.** Use the generated `FieldMap_Init/Main/Exit` and `NitroMain` source cuts to select the original lifecycle entry point. `FieldMap_Main` has five direct lexical call hints; only `OverlayManager_GetArgs` is present as a global native viewer symbol. The other hints connect location updates, zone changes and original per-frame dispatch. Reuse their original implementations, choose a coherent native/guest representation for field/object state, and implement only the required host services. A short direct call list does not imply a small transitive closure. Native startup replaces hardware initialization only where that replacement is explicit; it is not a claim that original `NitroMain` boots.
3. **Turn the walking demo into one game interaction.** Load original event objects/scripts and exercise an interaction followed by a door/map transition, with collision/object state preserved. Keep the current map/texture pipeline and input UI. Acceptance is a connected original game state transition, not another independently rendered subsystem.
4. **Save/load and one battle through the same owner.** Inventory the exact storage, script, sound and graphics boundaries reached by those flows; keep original save and battle rules. Evaluate ndspy for the new offline sound inputs before writing format tooling. Add host audio output after sequence/synthesis ownership is chosen.

Measure progress by new original gameplay paths reached, custom boundary surface removed, behavior preserved and complexity/performance of the connected session. Do not infer effort saved from dependencies installed, compile counts, hypothetical LOC percentages or renderer map counts. A complete boot/SDK minimum remains an open result to establish by linking and executing the chosen closure.
